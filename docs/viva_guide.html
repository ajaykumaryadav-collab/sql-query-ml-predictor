2. Problem Statement & Motivation

Database Query Optimizers (such as PostgreSQL's Cost-Based Optimizer) choose execution paths based on mathematical cost formulas derived from statistics (pg_statistic). While effective for basic queries, these estimators face fundamental challenges:

Challenge PostgreSQL Native Cost Estimator Our Machine Learning Approach
Measurement Unit Arbitrary unitless cost points (e.g. 100.5). Cost does not equal milliseconds. Predicts wall-clock time directly in milliseconds (ms).
Hardware Adaptation Static disk/CPU page costs (`seq_page_cost = 1.0`). Misses memory bus & CPU cache effects. Learns empirical execution behavior on the target physical/cloud hardware.
Estimation Drift Assumes column independence; errors multiply exponentially across multi-table joins. Ensemble trees capture high-order non-linear interactions across plan nodes.
Proactive Tuning Static advisory; requires manual DBA intervention to diagnose slow queries. Real-time bottleneck hotspot detection + automated index simulation with zero risk.

4. Machine Learning Pipeline & Mathematical Foundations

The model does not treat SQL as plain text (like NLP). Instead, it evaluates the physical relational execution plan generated by the query compiler. This guarantees query-invariant representations regardless of SQL syntax formatting.

A. The 29 Extracted Features (Feature Engineering)

Our recursive parser (feature_extractor.py) walks the entire PostgreSQL plan tree and extracts 29 numerical and structural features:

startup_cost total_cost plan_rows plan_width parallel_aware plan_depth number_of_plan_nodes number_of_tables number_of_joins number_of_filters number_of_sort_nodes number_of_aggregate_nodes number_of_seq_scans number_of_index_scans number_of_nested_loop_joins number_of_hash_joins number_of_merge_joins total_scanned_rows max_intermediate_rows total_tree_cost has_hash_join has_bitmap_scan number_of_bitmap_scans max_plan_width has_limit number_of_limit_nodes has_materialize output_to_scanned_ratio is_unbounded_scan

B. Mathematical Formulation & Target Log-Transformation

Query execution latency spans 4 to 5 orders of magnitude (from 0.05 ms to 500+ ms). Directly minimizing Mean Squared Error (MSE) would cause the regressor to fit only massive queries while ignoring smaller queries. To resolve this, we apply a Log1p transformation:

y_transformed = log(1 + actual_execution_time_ms) prediction = exp(model.predict(features)) - 1

9. Top 10 Viva Questions & Winning Answers

Q1: Why do we need Machine Learning when PostgreSQL already has a built-in cost estimator?
Winning Answer: PostgreSQL's native cost estimator uses static, theoretical formulas based on arbitrary cost units (e.g. 1.0 for sequential page cost). It does not output milliseconds. A cost of 100 could take 0.5ms on an NVMe SSD or 40ms under heavy disk I/O. Furthermore, static estimators assume column independence, leading to massive estimation drift on complex multi-table joins. Our ML model learns from empirical execution runs on actual hardware and directly predicts wall-clock execution time in milliseconds.
Q2: Why did you choose Histogram Gradient Boosting and Random Forest over Deep Neural Networks?
Winning Answer: Research consistently shows that for tabular, structured numerical data with non-linear relationships, tree-based ensemble models (Gradient Boosting and Random Forest) outperform Deep Neural Networks. They achieve higher accuracy with lower sample requirements, train in seconds instead of hours, do not require GPU hardware, and provide direct feature interpretability without the risk of overfitting.
Q3: Why did you apply a Log1p transformation to the target variable?
Winning Answer: SQL query execution times exhibit a heavy-tailed, exponential distribution spanning from 0.05 ms for indexed lookups to over 500 ms for large scans. If we trained directly on raw milliseconds, the regression loss function (MSE) would be dominated by high-latency queries, completely ignoring accuracy on sub-millisecond queries. By taking $y = \log(1 + \text{time})$, we normalize the variance and ensure balanced sensitivity across both fast and slow queries.
Q4: Why can percentage error look high on sub-millisecond queries?
Winning Answer: For queries executing in 0.08 ms, a difference of just 0.05 ms produces a mathematical error of over 60% due to the near-zero denominator. In real-world database systems, a 0.05 ms variance is completely negligible microsecond noise. That is why statistical standards for query regression focus on Mean Absolute Error (MAE = 3.92 ms) and $R^2$ Score (0.9462) rather than raw percentage error.
Q5: How does database buffer caching affect the ML prediction?
Winning Answer: PostgreSQL caches disk pages in its Shared Buffers RAM. The first time a query executes (cold cache), it may experience disk I/O latency; subsequent executions (warm cache) read directly from memory and run much faster. In our backend, we prime the buffer cache to measure consistent steady-state execution time, eliminating random disk latency spikes.
Q6: How does the What-If Index Simulation work without affecting production data?
Winning Answer: We leverage PostgreSQL's transactional DDL support. We open an explicit transaction block (BEGIN), create the suggested index, run EXPLAIN to measure the cost reduction on the new index, and immediately issue a ROLLBACK. The index is never permanently committed, zero production storage is used, and no locks are held.
Q7: How do you prevent SQL Injection and destructive queries?
Winning Answer: We implemented a strict whitelist validator in sql_validator.py. The backend verifies that incoming queries strictly begin with SELECT or WITH statements. Any query containing destructive keywords such as DROP, DELETE, UPDATE, INSERT, ALTER, or TRUNCATE is immediately rejected before reaching PostgreSQL.
Q8: How does the system handle continuous learning and model drift?
Winning Answer: The system logs query execution telemetry into query_history. Through the "Self-Tune from History" feature on the Metrics page, the backend extracts recent execution profiles, appends them to the balanced training dataset, and re-fits the model to adapt to newly introduced query patterns or data volume changes.
